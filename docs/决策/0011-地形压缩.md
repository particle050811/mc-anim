# 0011 地形压缩：区段换逐格预测压缩

## 格式 3（用户 11-02 定合并）

用户原话：「好的 早点合并吧」。旧目录一个字节不改。新附件未上传，**不能据此宣称其他机器已能 pull**；上传和推送还要用户点头，顺序是先上传再推送。

### 设计和取舍

保留格式 2 的遍历、整列、区间跳过、色板和块索引，只把逐格概率条件于状态类，并给字面值树训练初值。不是有损平滑，也不是跨区段字典。原型经第三批区段复核：主世界 87.10%、暮色 83.15%，解码约 ×1.04；这些是抽样，不替代下面的全包实测。

每包目录带一份 `模型.bin`，不是把模型编进代码。理由：地形按包内容寻址、按段声明进指纹，换一个世界的模型不应让全部地形段的代码指纹变；多个包的模型可以同时存在，Worker 按含版本的模型 URL 缓存。主线程一次下载、向各 Worker 广播一次，区段 Range 不重复带表。`assets pack/pull` 沿用整目录打包、清单验证，不需要新的远端接口。

表格式（小端）：`u32[MCQM, 1, 类数, 状态跨度]`，接 `u8[跨度]` 的状态类、`u16[类数×1371]` 的初值、`u16[类数×跨度]` 的字面值权重。类数固定 32；未见状态归 31、权重 1。中性表为类数 1、跨度 0 的 16 字节头，表示初值 1024、权重 1，仍走同一个解码算法。训练表不额外压缩：每包只下载一次、成本相对大包很小，少一条异步解表/解压路径；小包按全包真实字节择优，不把固定表成本藏在“区段比例”里。

训练顺序、每 L 抽 1/40、平局规则及小包 ≤1024 区段双编码择优，见 `docs/世界.md`。训练每包一次；烘焙用中性表暂存已固定的格子，再与转码共用定稿流程。因此状态号、遍历和写包顺序不受 Worker 完成先后影响。预测/跳过概率条件于 U/W/N/U 的状态类，整列概率仍共享；空间概率按 1/32 更新，字面值按 1/16 更新。训练用 8 次原上下文伪计数、16 次全局字面值先验平滑，沿用复核过的 32 类方案，不再调参迎合全包结果。没有新依赖，Remotion 4.0.537、three 0.186.1、AssemblyScript 0.28.20 不变。

格式 2 的 WASM 和初值冻结在 `pipeline/世界/烘焙/格式2*`，只给转码读历史包；不保留在 engine 中。引擎、查询只读格式 3，错版本或缺表都报错。模型参数改变只产生新包版本；解码语法变化仍要升格式版本。

### 验收边界

- 全包转码后从磁盘逐格比状态、群系和区段头，再登记；旧目录逐文件 sha 回读。
- 重新转码、烘焙/重烘、不同线程都应出同一目录指纹；小存档测试和正式包复验分开记。
- 真实浏览器 Worker 核同一批区段；画面严格比完整 PNG sha256，不用肉眼或容差。渲染只经全局渲染闸，转码 nice 10、2 线程。
- 尚未在 Windows 实机跑，不把“无原生依赖”写成 Windows 已验收；不访问 Release、不上传、不推送。
- 若完整下载节省明显低于约 10%，或真实渲染有稳定回退、任意指定帧 sha 不同，不值得直接合；不能拿抽样压缩率掩盖这些代价。

## 字节从哪来

- 算法（自适应二进制区间编码，LZMA 用的那种）公开，这里是自己写的，没有拷第三方代码。
- 编译器 `assemblyscript` 0.28.20（Apache-2.0，依赖 binaryen、long 也是 Apache-2.0），开发依赖、版本钉死。产物用 `--runtime stub`，模块里只有我们自己的解码函数，没有内存管理这类运行时；渲染、烘焙、转码都不装它也能跑，只有重编 WASM 才要。
- 复现：`pnpm install --frozen-lockfile && anim world 解码器 --检查`。编译选项写在 `pipeline/世界/区段解码器.ts`，它们进 WASM 字节。同样的源码换目录、换文件名编出来字节相同（2291 字节，sha256 `b47d73ed8014…`）。
- 模型初值：`anim world 解码器 --训练 主世界-116 暮色放大-1752-扩展 --抽 20`。按块文件名和文件内先后每 20 个区段取一个，数每个上下文 0、1 的频率。统计的是格子，和包是什么格式无关：从格式 1 的包学的表，和从转完的包再学一遍逐字节相同（10-31 核过）。
- 这两份是代码（小、改了要进指纹），所以进 Git，不走 `0002` 的数据根字节，也不走 `0005`、`0006`。地形包照旧挂 Release（`0006`）。
- `anim check` 比源码 sha（不要求装 asc）；`解码器 --检查` 才真的重编。

#### 放开裙边列

裙边那四圈分两类，都按「网格看不看得出」来证。

**邻圈（第 0、33 列，各级都做）**：本段从不出邻圈格的面，网格只拿它的挡面掩码（`occlusionMask`：整格、树叶、流体）去剔核心边格的面。所以邻圈里整格的可以换石头，掩码是 0 的非空气（花草、火把这类）可以归成空气，掩码不变。四种做法（整格全换／只换被埋的 × 归不归空）都量了：网格十一组（七组面加四组裙边）逐字节相同，随机 4883／4889 段、峡谷集 263／185 段全过，另一种树叶画法也全同。整格全换在主世界略好，只换被埋的在暮色略好（露在地表的整格换成石头后和旁边的核心边列不像，上下文变差），差不到 1 个点，编码器可以逐段取小的。同一格在两个区段里的两份抄本从此不一样；读方块的 `查询/源.ts` 只读核心列，不受影响。

**核心边（第 1、32 列，只做第 0 级）**：核心边上六面被埋的整格，网格只给它出朝邻圈的裙边面。换成石头以后裙边的贴图变成石头、并得更大，别的不变。

- 核对：每种材质前七组逐字节相同、四组裙边盖住的格位图一格不差，随机 1000／998 段、峡谷集 90／62 段全过。主世界换 1,253,263 格，裙边面 358,311 → 132,656，全部面少 5.1%（网格 391.8 MB → 372.0 MB，只省显存，裙边不画时没有光栅化开销）；暮色换 537,709 格，全部面少 0.9%。
- 裙边面露不露得出来：`世界.tsx` 只在那一侧同级邻段这一帧不在画时才画裙边。邻段换粗一级画时，被换的格朝着的邻圈格在第 1 级里的父格：主世界整格不透明 1,257,786、树叶 239（粗级树叶画成实心）、落在粗段 `k底` 以下且头顶实心 35,098、头顶不实 507；暮色 550,414、79、4,505、0。**反例（父格在粗段里却不挡）两包都是 0**，峡谷集也是 0。原因是粗级合并先比不透明度（`生成.ts` 的 `mergeKey`），第 0 级整格的格在第 1 级的父格必是整格或树叶，更粗的级照同一条递推。
- 唯一的例外是「头顶不实」那 507 格（主世界被换格的 0.04%，峡谷集里 67 格；暮色 0，峡谷集里 2 格）：粗段在那里最底一格不是实心、`k底` 以下又不出面，本来就有个看得穿的洞，从洞里看得到这块裙边，换了以后它的贴图从原方块变成石头。要不要为这点格把它们留着不换，转码时可以判（多查一次粗一级的区段）。
- 不放开的：粗级的核心边（粗段挨着更细的邻段时裙边真露得出来）；邻段不在包里的那一侧（包边，随机样本里 22／7 侧）。
- 画面上会不会变：几何上被父格整面挡住。已知对数深度写 `gl_FragDepth` 加 MSAA 时，侧对镜头的裙边墙会抢采样点（1 像素的线）；有这条线的地方，地表往下第二格起的颜色会从原方块变成石头。要在级别交界落在画面里的帧上出静帧或 `anim 认指纹` 验。

**渲染侧（只分析，没改）**：第四轮拆帧里 CPU 提交绘制（三次遍历、阴影和不透明提交、挂网格）每帧 101、37、74、80 ms（穿塔 200、穿塔 620、飞越、古卷），区段网格 28,995、8,378、23,573、26,826 个。64×64 网格数约降到四分之一，这一块按比例最多省 76、28、55、60 ms（帧时的 12%、10%、13%、16%），是上限：视野边上凑不齐 2×2 的降不到四分之一，每个网格里按材质、朝向分的组数不变。

代价：
- 视锥剔除和按朝向分组的剔除变粗，探进视野一个角的区段要多交三倍的顶点（没量，估顶点量多一两成）。
- 远近分级的交界从 32 米网格线挪到 64 米网格线，交界附近哪一级在画会变，**改画面**：全片认可、段签过期，要用户看。
- 加载和建网格的粒度大 4 倍：单个区段解码、建网格一次干四倍的活，首帧等区段建齐更集中；`地形用量` 的区段键、Range 取的粒度都变。
- 要改格式、重传 Release；两个包重烘，或者从现包四个拼一个（各子区段 `k底` 以下只能按石头算，和现在网格的规矩一致，拼出来的网格没核对）。

**和第四轮清单第 3 项的关系**：第 3 项「区段并进大缓冲、一类材质一次多段绘制」打的是同一块 CPU（101、37、74、80 ms），不改格式、不改画面，绘制调用不再跟着区段数走。它做了以后 64×64 在渲染上几乎不剩东西，只剩体积再小 11%～13% 和解码快几个点；先做 64×64 则第 3 项的余量只剩四分之一。两者技术上不冲突，收益不叠加。**倾向：渲染那一块走第 3 项，64×64 不为渲染做；只为体积值不值，等安全项转完包再看。**

要改的文件：`engine/voxel/区段.ts`（`sectionCells`、选区段、盒子）、`区段包.ts`（`paddedSectionCols`、块索引项数、`sectionInTile`、`sectionToVoxels`、`formatVersion`）、`区段包位置.ts`、`区段解码.ts`（写死的 1156、2312）、`网格.ts`（静态缓冲涨 4 倍）、`世界.tsx`（裙边开关、`drawAllMaxFaces`）、`地形用量.ts`；`wasm/区段解码.ts` 和 `区段解码器.生成.ts`；`pipeline/世界/烘焙/` 的 `区段编码.ts`、`写区段.ts`、`读区段.ts`、`模型.ts`（重训），`pipeline/世界/查询/源.ts`、`存档.ts`；`assets/地形版本.json`、资产锁、Release。

#### 做法 1：离线按视线留

规则：

- **镜头位置** = 露天格：头顶再没有整格不透明方块的非整格，峡谷底、露天坑、崖前、水里、树冠里都算。可以再加一圈屋檐带（露天格往外几格，见「两者结合和别的做法」）。镜头真进洞、进屋的地方照旧靠保真范围（那里的区段原样不动）；真做时保真范围里的非整格也要当镜头位置，从里面看得到的邻段才不会被填（原型里碰到保真区段的片直接跳过）。
- **看得见** = 从某个镜头位置沿直线到得了。算保守集（真可见集的超集），不靠采样。
- **余量** 1 格：保守集往外 26 邻的格也留，非整格方块朝着被填格的面、多重采样的边都不变。
- 其余的非整格填石头，再走安全项。

保守集怎么算、为什么不漏：一条直线穿过的格子是六邻相连、三个轴各不回头的一串；取分量最大的轴当主轴，主轴每走一步，另两个轴各至多走一步。按主轴和三个轴的正负分 24 个锥，每个锥顺着扫一遍，状态记「上次主轴走完以后另两轴走没走过」，从镜头位置起满足这条规则到得了的非整格都算看得见。真直线必满足规则，所以真看得见的格都在集里；集里多出来的是只有折线才到得了的格。单线程 JS 每格每遍 2.2～2.5 纳秒。

细锥（`--细 K`）：两个副轴再各按斜率分 K 档。斜率在 1/(t+2)～1/(t+1) 的线，两次副轴步之间主轴正好走 t+1 或 t+2 步；最后一档斜率不超过 1/K，至少走 K 步。状态改记「上次副轴走完以后主轴走了几步」，一共 24·K² 遍，仍是超集，比 24 锥紧。

精确还是采样：都不是，给的是有证明的上头（保守集）和采样的下头，真值夹在中间。下头 = 从洞格朝一批整数方向打线（每轴分量不超过 3、6、10，各 290、1730、7490 个方向），不撞整格走到露天格就算看得见，线上经过的格一并算。两头的差就是保守集可能多留的量；误伤（该留没留）按构造是 0，靠三项自查盯着：

**片边和二阶**。抽样是拼一片来算的，片外不知道，所以每个数有两头：「无边」（片外当没有镜头）和「片边当镜头」（片边两圈的非整格全当镜头位置）。真做是整级一遍扫过去，没有片边。主世界三片最深的大洞厅把四周从 128 米加到 256、384 米，「无边」留的洞格是 36,221 → 36,221 → 36,614（+1.1%），已经收住，下面都用「无边」的数；「片边当镜头」只是说明片边不能当镜头用（留出集留 1,749,642 格对 57,940 格）。二阶（一阶看得见的格都可能站镜头，想照顾屋檐下、洞口里）不收敛：同样三片从 128 米加到 384 米，留的洞格 212,770 → 874,168 → 1,349,670，漫进大半个洞穴网，不能用。

**跨级**。近处画第 0 级、远处画粗级，视线先穿过第 0 级的缝，再落到粗级的格上，所以粗级只在自己那一级里算会漏（上一轮洞深各级各截，也有这个毛病）。粗级合并是不透明优先（`合并.ts`、`mergeKey`：有一个子格整格不透明，父格就是），粗级的空都落在第 0 级的空里，混着画时的视线都是第 0 级里的视线。规则（「上并」）：粗级的格只要有一个第 0 级子格看得见就留，再并上本级自己算出来看得见的。例外是粗级存得比第 0 级深的格（它的 `k底` 按整个粗段最低的地表定，那里第 0 级没存、当实心，粗级是淹水的洞；占粗级空格的子格 0.2%～0.6%）和零星树叶压过原木的格，真做时把「任何一级是空的地方都当空」并起来扫一遍就都盖住。上并偏保守，粗级封着、第 0 级敞着的腔也会留。

**阴影和别的会不会变**。

- 直射的受光不变：太阳照得到的点，那条光线上的格都从线顶上的露天格直着看得见，不会被填；照不到的点，光线照旧要先穿过实心。
- 阴影图画的是背光面（`engine/voxel/材质.ts`），存的是光线从实心里第一次出来的深度。看不见的洞填掉以后，这个深度只会变深。软影（`级联阴影.ts`，近处约 18 厘米、远处约 1 米）采到「墙里头原来有个看不见的洞」的那几个样点会从挡变成不挡，墙根可能亮一点点，和墙里本来没洞的地方一样。余量治不了，**要在洞口、峡谷壁出静帧验**。
- 屏幕空间环境光遮蔽只看画出来的深度，不变。
- 合并出来的矩形切法会变（单位面不变），逐像素不保证相同，用 `anim 认指纹` 验。
- 自查里查出网格一处既有的毛病（和填洞无关，填洞让它显形）：贪心合并的键不含面在格子里的深度，半高的整格面（楼梯下半块的顶面）会和旁边同贴图、同类材质的整格顶面并成一张，深度跟最左下那格。暮色峡谷集 `0/-37/121` 高塔里有一段云杉楼梯，旁边倒放的那格楼梯被填掉以后，留着的两格楼梯的下半块顶面从高出半格回到自己的高度。主世界第 1 级 `1/68/8` 还有一张贴在格子上下面的花草类薄片，同样的原因差了一整格。自查单记成「面只换了深度」。现在的成片里凡是正放、倒放的同种楼梯或上下半砖在同一层挨着，其中一格的面就画高或画低半格（按合并的写法推的，没出图看）；改不改归渲染那边定。

**算一个包多久**。只扫存着的格（存的最高一层以上都是镜头位置，`k底` 以下是实心）：主世界第 0 级 81.1 亿格，24 锥单线程约 8 分钟；暮色 66.3 亿格约 7 分钟（按抽样实测的每格每遍 2.2～2.5 纳秒估，没真跑整包）。细锥 K = 3 是 9 倍（单线程约一小时），各遍互不相干，分给 8 个工人和 24 锥单线程差不多。内存：整级的实心位图和结果位图各约 1 GB，状态只留前一行。粗级从第 0 级的结果上并，另加各级自己扫一遍（格数是第 0 级的八分之一起）。

#### 做法 2：运行时剔除，不改数据

没做原型，只分析，没改渲染代码。

- **洞和地表分不开**。区段是 32×32 的整列全高，一个区段每类材质、每个朝向一份网格。Minecraft 那张可见性图靠的是 16 米立方的区段，洞和地表本来就在不同的区段里；我们要照做，得把每列切成 32 米一段：主世界第 0 级平均每列存 55 层、暮色 38 层，网格数平均翻一倍，有深洞的区段翻六到十倍，而提交绘制的 CPU 已经是每帧 74～101 ms（第四轮清单第 3 项）；连通又比视线松，峡谷边上的洞照样全算看得见。区段级的包围盒遮挡查询同理：整列的盒子总有一截露在地表上。
- **要按面分，离线那一遍省不掉**。不切区段的办法是离线把每段的面分成「露天看得见」和「进洞才看得见」两截，镜头在露天时只画前一截。这要算的东西和做法 1 一模一样，体积不省反增（多一层标记，格式要改），渲染省的和做法 1 相同。
- **显卡遮挡查询、层次深度用不上**。WebGL2 的查询结果要回到主循环才拿得到，同一帧里用就得停下来等；我们逐帧独立渲染（画面一致靠它），没有上一帧的结果可借。
- **剩下能省的本来就少**。光栅深度已经采用（主检出 `11c20fa9`，用户 11-15 定），被挡住的洞面不再着色，只剩顶点和阴影图那几毫秒；体积一个字节不省，而体积才是深洞占得最多的地方（主世界区段字节的一半）。

和第四轮的分工：这边管包里存什么，按视线填完，深洞的面在建网格之前就没了，显存、顶点、阴影跟着少；第四轮管每帧画什么，光栅深度、提交绘制合并（清单第 3 项）、整段被山挡住的区段剔除都在那边，洞不用它再管。两边的接口只有一条：渲染或 `anim check` 核对每帧镜头所在的格在镜头位置里（露天格、屋檐带）或在保真范围里，不是就报错（这是渲染和检查的代码，这里只提不做）。

#### 两者结合和别的做法

- **视线 + 洞口往里 N 米也留**（`--口`）：保守集之外，从露天格走六邻 N 米以内的洞格也留，镜头稍微探进洞口（没登记保真范围）时不至于看到石头墙。量了 16、32 米，见上表，主世界多不到半个点。这是唯一值得和视线合用的距离规则：距离只用来多留，不用来截。
- **视线 + 深处要采样确认**：保守集在暮色的深洞里偏松，离露天 128 米以外的格要采样线真看到了才留。数见上表。距离在这里只用来决定哪些格要多一道确认，但深处不再有证明。
- **包里留全、运行时按标记不画**：就是做法 2 第二条，体积不省。
- **洞深处只存粗一级**：被支配。看不见的洞存粗一级还是白占字节（约原来的四分之一），看得见的又不能降；渲染也不支持同一列里混两级。
- **按成片里镜头的航线算可见集**：能再省，但包就绑死在现有的成片上，新镜头要重烘，不做。
- **屋檐带**（`--带 4`）：露天格往外 4 格以内（走六邻、穿非整格）的格也当镜头位置，屋檐下、树干底下、洞口里几步的机位就都在证明里，不用逐个登记保真范围。量了：主世界留出集、峡谷集多 0.1～0.2 个点，暮色留出集不变，暮色峡谷集多 1.8 个点；面的自查 0。和洞口往里 N 米不一样：带是「镜头可以站这儿」，带里看得见的都留；洞口往里 N 米只是那 N 米自己留着。两样合在一起没量。
- **二阶**（一阶看得见的格都当镜头）不收敛，见上。再深的地方镜头要进去，登记保真范围。

**推荐做法 1**，镜头位置取「露天格 + 屋檐带 4 格 + 保真范围」，再加洞口往里 16 米：

- 它按「看不看得见」留，直隧道留、拐弯的洞填，不漏有证明，另有三项自查盯着。主世界约 267 → 148 MB，比洞深 128 米还小 5 MB；误伤从「没法量干净」变成「按构造没有」。
- 暮色只到约 254 MB，比洞深 128 米大 10 MB。这 10 MB 是保守集在深洞里放不掉的格，其中有确认看得见的；暮色本来也不是省字节的地方（安全项全做以后洞只占 2%～6%）。想要这 10 MB 可以加「深处要确认」，代价是深处没有证明，不推荐。
- 24 锥就够，不上细锥：多省 1～3 MB，算 9 倍。
- 屋檐带 4 格、洞口往里 16 米在主世界各花不到 1 MB，换机位的余地：前者让屋檐下、树干底下的镜头也在证明里，后者让镜头探进洞口时不会迎面撞上石头墙。
- 运行时剔除不做：体积不省，洞和地表在同一个区段里分不开，光栅深度以后也没多少可省。
- 渲染上别指望：每帧 1% 上下。这件事的收益是体积（主世界再少 119 MB）、解码和建网格跟着少。

用户 11-15 定不做（见「下一步」第 3 条）。

### 没做、拿不准

- 没渲染：变换 1、不截面的定底、邻圈的网格逐字节相同，画面不该变；变换 3 少了面，对数深度加 MSAA 下原来被腔壁挡住的缝有没有漏，只有静帧能证；核心边换了裙边的贴图，见上。
- 地下查到的是石头：`anim world block|slice`（`pipeline/世界/查询/源.ts`）在埋住的地方不再是真方块。以后要在保真范围外挖地，得回存档重烘那一片。
- 模型表没重训（换完石头变多，重训还能小一点，没估）。换进去的方块按包选最常见的整格方块可能更小，下界没有石头必须另选。
- 留出集和随机样本对第 0 级的估计差约 2 个点，全包的数以真转为准。解码计时时机器上另有渲染计时在跑，只能看个大概。
- 洞深、视线、64×64 的渲染收益都是照第四轮拆帧的数按比例推的，没跑过一帧。
- 视线（第三轮）只在抽样的片上算过：整包没真扫，耗时和内存是按每格每遍的纳秒数估的；全包的 MB 是抽样比例乘出来的。原型跳过了含保真区段的片，保真范围里的格当镜头位置以后旁边会多留多少没量。
- 视线填完以后的软影（墙里原来有看不见的洞的地方）、合并矩形的切法没渲染过，要静帧和 `anim 认指纹`。
- 暮色的保守集在深洞里是偏松还是真看得见，没分清（保守集认 296,102 格，采样只确认 6,420 格）。
- 「镜头所在的格在镜头位置或保真范围里」的核对没做；现有成片的机位有没有落在外面的，没查。
- 网格合并的键不含面在格子里的深度（见第三轮「阴影和别的会不会变」），是既有的毛病，没改、没出图。
