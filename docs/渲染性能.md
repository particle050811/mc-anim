# 渲染性能

母版渲多快、慢在哪、改过什么。数都是 MacBook Air（M 系列，10 核，32 GB）上渲视频级、并发 1 量的。

## 平时怎么看

每次 `film` 出切片、`still`、`bench` 都自动记，不用加参数：

```
./anim 耗时                 最近 20 次，一行一条：总秒、帧数、每帧中位、P90、首帧、等得最多的
./anim 耗时 <段> [--最近 <n>]   这段最近一次（或几次）的完整报告：阶段、每帧分布、等得最多的 delayRender、最慢的帧和它们在等什么、机器负载、内存、最高芯温和最高发热等级
```

- 每帧明细在 `run/logs/渲染明细/*.json`：一帧约 100 字节，穿塔这种 2000 帧的一份约 200 KB，只留最近 300 份，写的时候回收。JSON 里 `帧[].等` 是这帧等过的 delayRender（短于 20 毫秒的只进总表），`系统` 是每 10 秒一次的负载、空闲内存、换出、浏览器和 ffmpeg 的内存和 CPU（Windows 没有 ps，这几项是 null）。同一轮采样带 `芯片最高温`（°C）、`发热等级`；渲染开始、结束各补一个点，`系统[].时点` 区分开始/采样/结束，`秒` 相对渲染开始（保留毫秒精度，可对照累计每帧耗时），顶层 `温度` 汇总开始、结束、采样最高值。结束指 renderMedia/renderStill 返回，不含后续转存；峰值只是采样中最高，不声称抓到两点间的瞬时尖峰。读不到的项为 null，旧明细不补造温度。
- 11-06 以前后台转存时，放闸即停表并先写一份明细，后台收工写回同一文件补齐派生段签、转存等阶段；那时的明细第一份没有转存阶段是正常的。11-06 起没有后台转存（`决策/0014`），段签在闸里派生，明细一次写全。
- 失败的渲染没有明细，温度看调度月日志的 `拿锁`、`放锁`。
- 分阶段的历史在 `run/logs/阶段耗时.tsv`，追加写、不回收，一次渲染几十行。外层阶段包含里层：打包含备素材、webpack；段签含「段签：」开头的几步。11-06 起每段在闸里依次 出帧、编码、查帧数、声音、段签（`决策/0014`）；以前的记录里 派生段签、转存 在后台子进程里和出帧同时跑（`决策/0008` 末节），加总超过墙钟是正常的，`等后台` 是出帧为后台多等的，每帧明细的后台内存、CPU 另列一行。`anim 耗时` 不带段时列最近几批的账。
- 帧的毫秒是相邻两次 onProgress 的差，含截图和交给编码器；delayRender 会重叠，各标签加起来不等于出帧合计。

## 怎么测

```
./anim bench <段> [--帧 <起>-<止>] [--次 <n>] [--详细] [--输出 <json>] [--不收日志] [--留输出 <目录>]
```

- 照母版的渲染参数渲一段帧（默认前 100 帧），分开报打包、开浏览器、读 Composition、首帧、出帧、收尾，再报每帧耗时的中位数、P90 和最慢的 5 帧。不写母版缓存、不按段记耗时，走渲染闸（`pipeline/渲/测速.ts`）。
- 缺求解缓存时先补写、等写完再测读组合和出帧；这次冷启动不计入各测速阶段，终端和结果的 `求解缓存准备` 单列新写份数、准备秒数。已有缓存时不额外读组合。
- `--详细`：Remotion 开 verbose，日志写到 `<输出>.log`。里面有 Remotion 自己报的各步耗时，比如「Seeking to frame N took …」，每个 delayRender 拦了多久（「Waiting for R3F to render frame」「体素世界：还有 N 块区段」）。
- 结果的 `共享内存` 表示实际出帧采用 Remotion 共享内存输入（FFmpeg 的 `remotionshm`），不是“未主动禁用”；FFmpeg 不支持或浏览器回退到截图时为 `false`。每轮各记一次，顶层为所有轮都使用共享内存时的 `true`，不受日志级别影响。
- `--关共享内存`、`--浏览器 <chrome-headless-shell>`：拆 Remotion 版本差异时用，母版不用。
- 渲染用的浏览器（Remotion 带补丁的 chrome-headless-shell）放数据根 `cache/浏览器/<Remotion 期望版本>/`，各 worktree 共用，重装依赖删不到（`pipeline/渲/浏览器.ts`）。缺了先从本检出的 `node_modules/.remotion` 克隆，没有才让 Remotion 下载；下载不通就从别的检出或机器把那个目录整个拷来。`anim doctor` 的「渲染浏览器」一项报它在不在。旧版目录（如 `149.0.7790.0`）留给 `--浏览器` 做对照。
- `--不收日志`：renderMedia 退回 logLevel error，量记日志的开销用；不采样，没有 `系统` 和 `温度` 读数（JSON 的 `系统` 为空数组，不写 `温度`）。`--留输出 <目录>`：留下渲出来的 mp4，比两版的像素用。
- **比耗时要看温度**：无风扇机器即使 CPU、内存占用差不多，也可能因热降频变慢。用同级别同段交替测，先对照开始/结束/最高芯温、最高发热等级，再沿 `系统[].秒` 与每帧耗时找变化；仅凭温度高不能断言已经降频，实际频率未接入。取值方式和告警初值见 `调度.md`。
- 别的 worktree 也在跑重任务时，数会飘（10-30 量的时候负载到过 30）。比改动前后，要背靠背轮流跑，只比同一时段量的数。

## 回收顶点容器、共用索引、碎渣（10-31 落地）

a、i、c 落地，b 没动。每帧画出来的字节不变，但 `engine/voxel/` 和 `库/特效/方块飞溅.tsx` 变了，用到它们的段指纹都会变，要重渲一次。

- **a 回收容器**（`engine/voxel/容器池.ts`）：区段网格改用 three 公开的 `GLBufferAttribute`，容器自己管。不走原型那样包 WebGL 接口：只有区段网格进池，索引容器和别的模型碰不到。
  - 大小：`bufferData` 每次整个重新分配只在 Metal 上成立；Vulkan、D3D11 上容器的存储只涨不缩，所以取壳只取「装到过的不超过这次要装的」（11-14 改，见「从头渲到后面显存越攒越多」）。
  - 显存：还回来时清成 0 字节，Metal 上池里只是空壳；Vulkan、D3D11 上空壳还占着旧存储。空壳最多 2 万个、装到过的字节合计最多 128 MB，超了从最大的真删。
  - 何时传：第一次被哪个视锥碰到才传（`intersectsFrustum`），和 three 自己管时传的是同一批。先试过建网格时就全传，RSS 看着更高，改了。
- **i 共用索引**（`releaseVoxelMeshes`）：释放前先把索引和属性从几何上摘掉，`dispose` 不会连带删，少传每帧 1.57 MB。

## 重渲不一致（10-31 查明并修复）

同一份代码渲两遍，6-斩娜迦、6-起飞、6-进入森林有帧差几个到几十个零散像素，四轮能出 4 个版本，是真随机。

- 根因：导出网格（`engine/voxel/方块网格.tsx`）算贴图级别时，对质心插值的 `vLocal` 求导。质心插值的变量在面边上导数不可靠，要同时开多重采样才会出现。关多重采样、或改用普通插值的变量求导，都能让它消失；关阴影、关镂空、关花草、每 200 次绘制 flush 或 finish 都不能。
- 排除过的：挑到的区段、绘制顺序、镜头矩阵、3754 块网格的内容、每帧 `gl.render` 次数，两轮完全相同。
- 修法：级别按普通插值的 `vLocalD` 算，取色继续用质心插值的 `vLocal`（防边缘取到旁边贴图的作用不变）。多重采样不能关：全片边缘会变硬发闪，用户看过的画面都要变。
- 验证：3 段共 492 帧各 3 轮，逐帧 PNG sha 全同；耗时在波动内（斩娜迦 47.7～53.4 秒，修前 48.5～51.4 秒）。
- 代价：和修前比，有导出网格的帧约 2～3% 的像素变了，差 16 级以上的零散落在方块边和幽匿块这类高对比贴图上，放大对比肉眼几乎看不出来。这是一次性的。11-01 全片抽帧量到差 16 级以上最高 0.25%（7-音波），超过 verify 的 0.1% 门槛，15 段因此不过；在撤掉这个修复的工作区重渲后都过了，所以差确实来自这里。
- 同时修了挑区段用上一帧视野（`engine/voxel/世界.tsx` 摆完镜头补更新世界矩阵）：这三段逐帧 492 帧里只有进入森林 60 帧差 1 个像素 1 级，所以母版以前没有明显缺地形。

## 从头渲到后面显存越攒越多（11-14 查明，修了容器池）

**现象：** 笔记本（8 GB 显存，Vulkan）从第 0 帧渲 6-穿塔斩首领，两次都在约第 2400 帧丢 WebGL 上下文。GPU 进程专用显存开跑约 3.4 GB，只升不降到 6.7 GB；冷启动只渲 2300～2480 帧峰值 4.8 GB，没事。Mac 上 GPU 进程足迹在 4.7～5.9 GB 来回，不涨。

**原因：ANGLE 的 Vulkan、D3D11 后端，容器（WebGLBuffer）的存储只涨不缩。**

- `bufferData` 传 0 字节是空操作；传得比现有存储小就沿用旧存储；只有传得更大、换用途或 `deleteBuffer` 才重新分配（Vulkan 看 `BufferVk::setDataWithMemoryType`、`shouldRedefineStorage`；D3D11 看 `Buffer11::NativeStorage::resize`，只读了源码没试）。Metal 每次 `bufferData` 都按新大小另取。
- 合成试验（同一个 headless shell 157，`--use-angle=swiftshader` 走 Vulkan 后端，量 GPU 进程足迹）：建 1500 个 × 256 KB 后 433 MB → 全部清成 0 字节 433 MB → 全部重传 1 KB 434 MB → 全删 70 MB。Metal 上重传 1 KB 后 56 MB。Vulkan 上换装更大的数组旧存储会放：64 KB 换 256 KB，152 → 434 MB，不叠加。
- 旧容器池的空壳拿到哪个用哪个：装过大数组的壳去装小数组，大存储一直占着；壳在区段之间轮转，每个都涨到它装过的最大一次，池里的空壳也占着旧存储。

**按这条规则记的账**（Mac，`anim bench 6-穿塔斩首领 --帧 0-1500`，页面里临时包一层 WebGL 接口，记每个容器装着多少、存储按规则有多大，MB）：

| 帧 | 区段顶点逻辑字节 | 旧池：在用 + 空壳 | 新池：在用 + 空壳 |
|---|---|---|---|
| 0 | 1539 | 1539 + 0 | 1539 + 0 |
| 300 | 1081 | 2536 + 0 | 1081 + 119 |
| 600 | 370 | 753 + 976 | 370 + 124 |
| 1000 | 1033 | 2995 + 0 | 1033 + 120 |
| 1300 | 669 | 2426 + 311 | 669 + 122 |
| 1500 | 1092 | 3176 + 0 | 1092 + 112 |
| 冷启动第 1300 帧 | 670 | 670 + 0 | |
| 冷启动渲到 1500 | 1092 | 1862 + 0 | |

旧池多占的从第 300 帧 1.45 GB 涨到第 1500 帧 2.08 GB（每个容器平均轮转 9.4 次），和笔记本「从头渲比冷启动多约 1.9 GB」量级对得上。这是在 Mac 上按规则算的账，不是在 Windows 上量的显存。

**修法**（`engine/voxel/容器池.ts`）：记每个容器装到过的最大字节数，空壳按它分档；取壳只取装到过的不超过这次要装的，后端要么原样复用、要么按这次的大小重新分配，在用的容器不多占。空壳在个数上限之外再按装到过的字节合计 128 MB 封顶，超了从最大的删起。Mac 上 0～1500 帧 982 秒对改前 980 秒，每帧中位 615 对 609 毫秒；容器多建约 7 万个（19.0 万对 11.7 万），每帧约 50 个。

**一起修的：区段网格的 CPU 数组被缓存钉住**（`engine/voxel/世界.tsx`）。`kept` 超上限挤掉记录时只从表里删，缓存里的条目还指着这条记录，数组放不掉；开超远景一帧 1200～1900 万面，`kept` 上限 700 万面，等于没管住。改成挤掉时清掉记录上的数组（后台建区段那一轮先把网格拿在手上）。Mac 上渲染页进程足迹，0～1500 帧每 2 分钟均值：改前 4.7 → 6.7 GB（峰值 7.4），改后 4.1～4.6 GB（峰值 5.4，在第一分钟）。

## 跨机器画面差异（11-02 查明）

同一提交、同一帧，Mac 和笔记本出图不同。两边 75 个数据文件逐字节相同，第 580 帧的 2605 个区段、13,168 个网格、1,755,774 个三角形相同；差异出在着色器的数值。

- **取错贴图（白纹）：** `engine/voxel/真实方块图集.ts` 的 `atlasUv` 按 `mod(layer,16)`、`floor(layer/16)` 拆行列。Windows 上 D3D11、Vulkan、OpenGL、WARP 插值后贴图号都带小数，Mac 是整数（第 580 帧非整数 <0.02%）。每行第 0 列的贴图（共 155 张）偏一点就拆到上一行末列：黄花叶 2384 取到白凳子 2383 的边列（上白下棕、alpha 255，镂空被填满），白桦叶 64 取到白桦门 63。修法是拆之前 `floor(layer + 0.5)`，对整数输入 0～65535 全不变。已合进 main（`9f261a4`）：15 段指纹变了，Mac 上重渲后 39 段视频流和旧母版全部相同，38 段整个文件逐字节相同（穿塔差在音频，见「同一代码的音频有两版」）。
- **随机朝向：** `engine/voxel/材质.ts` 可转方块顶面的朝向用 `fract(sin(dot(floor(vW.xz), vec2(127.1,311.7)))*43758.5453)`。坐标约 (-5950,-3905) 时点积约 2e6，两机算出的朝向互不相关（同向约 20%）；NVIDIA 编出 FMUL.RZ+MUFU.SIN，只有 32 种取值，D3D11 对 Vulkan 也有约 13% 的格朝向不同。打补丁后差 16 级以上的像素约八成来自这里，其余在阴影里的树叶、原木边和接缝漏光。换整数哈希能修，但会改 Mac 上看过的画面，要用户点名。
- **补丁后飞越 580：** 差 16 级以上 1.59%→1.02%，PSNR 34.6→39.2。
- 着色器里不要依赖「插值后还是整数」或「大参数的 sin」，跨显卡结果不同。
