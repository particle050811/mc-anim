# 取材 mod（mcai）

让 AI 用命令行控制 Minecraft 取材：摆机位、截图存文件、冻结世界、放方块、撤销。
由两部分组成：

- **mod**（`src/`）：Forge 1.20.1-47.4.10 的 mod，在游戏里开一个只监听本机的 HTTP 接口 `127.0.0.1:25590`（每个实例一个端口，默认实例是 25590）。
  客户端和取材服务端都装：服务端上只做两件事，给装了「暮色放大4倍」数据包的世界放大暮色森林的地标网格（见「暮色森林放大 4 倍」），
  给放了「主世界修整」数据包的世界提供生成时修整用的两种密度函数（见「主世界生成时修整」）。
- **`mcai`**（`sourcing/mcai/mcai.py`）：单文件 Python 命令行（只用标准库），调这个接口，并负责游戏外的事：启停游戏、看日志、编译安装、停服务端。
  本仓库里用 `sr mcai <动作…>` 调：sr 先过资源闸（开游戏时），再把游戏环境、JDK 这些按 sr 配置用 `MCAI_*` 环境变量传给它。

> 本手册从旧项目搬来。文中 `game/…` 指游戏环境目录（sr 配置 `SR_GAME`，mcai 读 `MCAI_GAME`，迁移期是旧项目的 `game/`）；
> `参考模型库/…` 开头的工具（取材服务端.py、选种、预生成看守.py 等）还在旧项目里，`sr world` 做好后再搬。

游戏只用来取材（参考图、量尺寸），不是成片。主用法是单人世界：把取材服务端的世界（`game/取材服务端/<世界>`）复制成客户端实例里的“片场存档”，只改复制品。服务端怎么建世界、预生成见「取材服务端」一节。

## 典型用法

```sh
sr mcai build                                   # 编译并装进 game/实例/取材客户端/.minecraft/mods/
sr mcai game copyworld name=片场 from=<世界>       # 把 game/取材服务端/<世界> 复制成存档「片场」（from 必须写；已有则加 overwrite=1 重置）
sr mcai game start world=片场                    # 起游戏、直接进存档、等到可以接命令（约 30 秒）

sr mcai cam pos=264,100,488 pitch=90 yaw=180 dim=twilightforest:twilight_forest   # 娜迦庭院正上方俯视，画面上方朝北
sr mcai freeze                                   # 冻结世界
sr mcai cmd effect give @s night_vision infinite 0 true    # 暮色森林很暗，对照贴图先给夜视
sr mcai shoot out=../参考模型库/预览/实机对照/俯视.png
sr mcai batch "cam pos=222,52,548 look=264,0,488" "shoot out=../参考模型库/预览/实机对照/斜视.png size=3840x2160"

sr mcai fill from=250,1,490 to=262,12,500 block=minecraft:gold_block
sr mcai undo                                     # 撤销上一步
sr mcai game stop                                # 正常退出游戏（会存档）。忘了也会在空闲 30 分钟后自己退，见「空闲自动退出」
```

`mcai help` 列出全部动作和参数（游戏开着时，从 mod 的注册表实时生成）；`mcai --help` 是游戏外子命令的说明。
每个动作的输出都是 JSON；失败时退出码非 0，并打印「失败：原因」。

## 取材服务端：建新世界、预生成、复制成片场

`game/取材服务端/` 是无界面的 Forge 1.20.1 服务端，`mods/` 里会影响世界生成的模组和整合包一致（暮色森林、冰火、匠魂、机械动力、车万女仆、夸克 + Zeta），
只差 Lootr：它会把结构里的宝箱换成 Lootr 箱子，没装。整合包里其余没装的 Cloudertinker、twilight_construct、拔刀剑、Epic Fight、YSM、JEI 不碰世界生成。
用 `参考模型库/工具/游戏取材/取材服务端.py` 起服、按顺序发命令、停服，参数见文件头。能同时开几个看资源：长任务用 `python3 参考模型库/工具/资源闸.py <命令>` 包一层，CPU 负载和空闲内存够就放行，不够就等（用户 2026-10-04：资源允许就能开多少开多少，负载太大再一个一个来）。
停服时先发 stop 等它存完盘（最多 300 秒），Ctrl-C、`kill`（SIGTERM）也一样，之后撤掉预生成模组、改回 server.properties。
别用 `kill -9`：没存盘的区块会丢，Chunky 的进度却可能已经记过它们，`chunky continue` 会跳过，世界里留下空洞。

- 旧的 `world/`（种子 20260930，普通世界类型）不动。2026-10-04 换真实地貌以后，主世界和暮色各建一个世界（各自的种子）：
  暮色世界放在 `game/取材服务端/` 里旧世界旁边；主世界放在主世界专用服务端 `game/取材服务端-主世界/` 里（见下一节），用 `--server 取材服务端-主世界` 选它。
  分成两个世界是因为结构开关（level.dat 里的 generate_features）一个世界只有一份，管世界里的所有维度：主世界要结构全禁，暮色的地标必须生成。
- **建新世界**：`--new` 必须写明是哪个世界，种子、世界类型、结构开关只在建世界那一次临时写进 server.properties，服务端就绪后原样改回，
  之后都存在 level.dat 里，建错了只能删掉重建。
  ```sh
  python3 取材服务端.py --server 取材服务端-主世界 --world <世界名> --new --seed <种子> --no-structures   # 主世界：结构全禁
  python3 取材服务端.py --world <世界名> --new --seed <种子> --twilight-x4                                # 暮色：结构照常，放大 4 倍
  ```
  - `--type` 默认 `minecraft:normal`：地形模组改的是普通世界的地形，巨型生物群系（`minecraft:large_biomes`）和 Tectonic 互斥，配上它会悄悄得到原版巨型群系的地形。
  - 数据包在第一次启动前放进新世界的 `datapacks/`。`sourcing/datapacks/` 下 `通用/`、`只给主世界/` 两组：
    `通用/`（两个世界都放）：`不生成龙巢`，冰火的地表龙巢、龙穴洞穴不生成；
    `只给主世界/`（`--no-structures` 才放）：`主世界不生成人造地物`，关掉不归 generate-structures 管的人造 feature（原版沙漠水井、地牢，冰火独眼巨人洞、精灵村、塞壬岛、九头蛇洞、蚁巢、龙骨架）
    和冰火生成区块时直接刷生物的 5 个 feature（死亡蠕虫、海马、海蟒、铜羽泽鹗、游荡独眼巨人），清单和原因写在它的 `pack.mcmeta` 里。
    `--twilight-x4` 另放 `sourcing/datapacks/暮色放大4倍`，要求服务端 `mods/` 里有 mcai 的 jar（见「暮色森林放大 4 倍」）。
    `--no-structures` 默认另放 `sourcing/datapacks/主世界修整`（生成时修整，见「主世界生成时修整」），要求服务端 `mods/` 里的 mcai 含修整；
    `--no-terrain-edit` 不放，只给对照、测试用。世界里有用到修整的数据包时，启动前查 jar、开服后查 `/datapack list`（修整包要启用、排在史诗地形之上），
    日志里出现数据包读不进来的行（注册表加载出错、未知的密度函数类型、安全模式）就停服报错。
  - 主世界只能建在主世界专用服务端里，在 `取材服务端` 里加 `--no-structures` 会拒绝：那里没装地形模组，建出来是原版地形。
  - level-name 一直是 world，但开哪个世界都要写 `--world`（旧世界写 `--world world`）；世界不存在又没给 `--new` 会拒绝，
    不然服务端会拿 server.properties 里旧世界的种子悄悄建一个、结构照常、也不带数据包。
- **预生成**：Chunky（完整区块）和 Distant Horizons（远景 LOD）放在服务端目录的 `预生成模组/`，平时不装，
  用 `--pregen chunky` 或 `--pregen dh` 只在这一次装上。两个不能一起装，一起装启动必崩。
  ```sh
  python3 取材服务端.py --world <世界名> --pregen chunky 'chunky world minecraft:overworld' 'chunky center 0 0' 'chunky radius 1000' 'chunky start' 'wait:Task finished for'
  python3 取材服务端.py --world <世界名> --pregen dh 'dh pregen start minecraft:overworld 0 0 128' 'wait:Pregen is complete'
  ```
  暮色维度写 `twilightforest:twilight_forest`。跑得久的放后台。Chunky 的任务进度存在 `config/chunky/tasks/<维度>.properties`，按维度存、不分世界，
  换世界之前要么跑完，要么 `chunky cancel`。
  2026-10-04 实测（同时有别的任务占着约 6 个核）：Chunky 主世界约 45 区块/秒、约 42 MB/km²，暮色约 90 区块/秒、约 26 MB/km²；
  DH 主世界约 40 区块/秒、暮色约 100 区块/秒，LOD 主世界约 12 MB/km²、暮色约 7 MB/km²，但它还会往 region/ 里写 structure_starts 半成品区块
  （主世界约 20 MB/km²），合起来约 32 MB/km²，比 Chunky 只省四分之一左右。DH 不比 Chunky 快，也省不了多少硬盘，看得到的范围都用 Chunky。
  DH 在暮色生成黑暗之塔时会出错（`DarkTowerMainComponent.makeFurnacePillar` 往熔炉里放东西，DH 的 FEATURES 生成环境里拿不到熔炉的容器，抛 NPE），
  那几个区块的 features 整步没生成，LOD 里缺东西；暮色地标附近一定用 Chunky。
  跑得久的预生成用 `参考模型库/工具/游戏取材/预生成看守.py`（用法见文件头）：它每次起服前过资源闸，每分钟看一次堆和日志，
  老年代占到最大堆的 90% 以上又在 Full GC、或者日志 10 分钟不动（先存一份 jstack），就正常停服再 `chunky continue`；跑完重新起服把同一个选区再扫一遍补洞。
  选区命令后面写 `expect:<Chunky 的回话>`（`取材服务端.py` 的命令，30 秒内日志里没出现就停服）确认每条都生效了。
  看堆别用 `jstat -gcutil` 的 O 列：G1 下那是老年代占「当前分到的」老年代的比例，刚起服就八九成；要拿 `-gc` 的 OU 除以 `-gccapacity` 的 OGCMX。
  `--gen-threads N` 把区块生成的后台线程（Worker-Main-N）限成 N 个（`-Dmax.bg.threads`，默认核数 − 1），几路同时渲染时给渲染留核。
  Chunky 1.3 除了方形、圆这些形状，还能按列表生成：`chunky pattern csv <名>` 读服务端 `config/chunky/<名>.csv`（一行一个区块 `cx,cz`，按文件里的顺序），
  名字只能是 ASCII 一个词；Chunky 仍拿选区的形状筛一遍（区块中心落在形状里才生成），选区要包住列表里的全部区块。斜着的走廊用它，比拿正方形拼省得多。
- **复制成片场**：`sr mcai game copyworld name=片场 from=<世界名>`。from 必须写：写世界名就到 `game/取材服务端/` 下找，也可以写世界目录的路径
  （主世界写路径，如 `from=../game/取材服务端-主世界/<世界名>`）。数据包、DH 的远景数据库都在世界目录里，会一起带过去。
- 新世界里有夸克的方块，客户端没装夸克就打不开，所以两个客户端实例 2026-10-04 补装了和取材服务端同一版的 Quark-4.0-462、Zeta-1.0-31（jar 在 `game/缓存/mods/`）。
  `quark-common.toml`、`zeta-common.toml` 也从取材服务端的 `config/` 拷了过去，三处一字不差：夸克的世界生成开关都在 `quark-common.toml` 里，
  客户端的集成服务端补生成区块时要和服务端生成的对得上。以后改了服务端的夸克配置，同样拷给每个客户端实例。
  夸克的客户端模块（`[client]` 一节）照默认全开，其中 Greener Grass 会把草和树叶的颜色调绿（`color_matrix` 绿 ×1.11、红蓝 ×0.89），截图和 `mesh` 导出的草叶颜色跟着变。

1. **复制服务端**：从 `game/取材服务端` 复制一份，世界（有 level.dat 的目录）、日志、Chunky 的任务进度都不带（项目根下执行）：
   ```sh
   cd game
   ex=(--exclude=/logs/ --exclude=/crash-reports/ --exclude=/server.out --exclude=/config/chunky/tasks/)
   for d in 取材服务端/*/; do [ -f "$d/level.dat" ] && ex+=(--exclude="/$(basename "$d")/"); done
   rsync -a "${ex[@]}" 取材服务端/ 取材服务端-主世界/
   ```
   预生成模组跟着带过去，`--pregen` 照常用。端口改成了 25598（暮色那个是 25599），两个能同时开。
   主世界服务端也装 mcai：读方块碰上调色板扩容就重读的修复对主世界预生成一样要有，生成时修整也要它（没有就读不进修整包，服务端起不来）。
   `sr mcai build` 会装进所有 `game/取材服务端*/mods/`。
2. **建客户端实例**：`sr mcai game newinstance name=取材客户端-主世界`（从 `取材客户端` 复制，夸克、Zeta 和它们的配置跟着带过去）。
   拍主世界远景要用 DH 的话，再 `sr mcai game newinstance name=取材客户端-主世界-远景 from=取材客户端-远景`。地形是数据包、跟着世界走，客户端实例不用另装；
   但修整包要 mcai 认得，打开这个世界的实例都要装含修整的 mcai（`sr mcai build` 装进所有实例），见「主世界生成时修整」。
3. **装地形**（只装进这一套）：史诗地形 compatible 1.0.3 是数据包（`epicterrain_compatible1.20.zip`），不装进 mods/。
   zip 放在 `game/取材服务端-主世界/世界数据包/`（`game/缓存/数据包/` 另留一份），`--new` 在第一次启动前把它拷进新世界的 `datapacks/`；
   `世界数据包/` 里没有数据包时 `--no-structures` 会拒绝，免得建出原版地形。离线选种（`参考模型库/工具/选种/地形.mjs`）读的也是这一份，换包两边一起换。
   数据包跟着世界走，客户端不用装。它的高度到 y511，导入范围要跟着放大。
4. **建世界、复制片场**：`python3 取材服务端.py --server 取材服务端-主世界 --world <世界名> --new --seed <种子> --no-structures`
   （默认带上 `主世界修整`；修整包的区域定稿以前别建正式的主世界：已经生成的区块不会跟着包变），
   建好后核对服务端的 `logs/latest.log` 里有 `Found new data pack file/主世界不生成人造地物`、`file/epicterrain_compatible1.20.zip` 和 `file/主世界修整`、
   level.dat 的 generate_features 是 0（修整包启用、排在史诗地形之上，脚本开服后自己查）；
   片场用 `MCAI_INSTANCE=取材客户端-主世界 sr mcai game copyworld name=片场 from=../game/取材服务端-主世界/<世界名>`。

## 多个 Agent 同时用

- **共用一个实例（平时用这个）**：几个 Agent 对同一个游戏发命令，会动镜头、改世界、截图的动作排队一个个做，`help`、`ready`、`state` 不排队。
  镜头只有一个，所以“摆机位 + 截图”要写进同一个 `batch`（整个 batch 算一个动作，别人插不进来）；分两条命令发，中间可能被别人的 `cam` 挪走。
  冻结状态和撤销栈也是共用的：`undo` 撤的是最近一次改动，不管是谁做的。
  `game start world=片场` 在游戏已经开着同一个存档时直接复用；存档不同会拒绝。`game stop` 会把别人正在用的游戏也关掉，关之前确认没人在用。
- **一人一个实例**：`sr mcai game newinstance name=<实例名>` 复制出一个新实例（同一批模组，约 150MB，端口自动分配，写在实例的 `config/mcai.port`），
  之后所有子命令前加 `MCAI_INSTANCE=<实例名>`。各实例有各自的镜头、世界（各自 `copyworld`）、撤销栈。`sr mcai game instances` 列出所有实例的端口和状态。
  **两个客户端同时开（其中一个带 DH）吃不消**（2026-09-30 实测：10 核的 1 分钟负载到 70，交换区用掉 5G）。无界面服务端轻得多，和别的任务能不能并行按资源闸看负载。
- 现有实例：`取材客户端`（默认，日常取材）；`取材客户端-远景`（多装了 Distant Horizons 3.3.3，只在拍宏大远景时开，远景逐步生成、很吃 CPU）。
  远景实例刚启动的头十几秒，DH 还在把存好的远景一级级读进来，这时拍到的中景是粗色块；等一会儿再拍。
- 两个实例都装了夸克和 Zeta（2026-10-04，见「取材服务端」一节最后一条）。
- 两个实例都装了优化模组（2026-09-30）：Embeddium 0.3.31（区块渲染）、ModernFix 5.27.83、FerriteCore 6.0.1、Canary 0.3.3。
  装完后窗口隐藏空转时 CPU 从约 2 个核降到约 0.3 个核；截图、`mesh`、DH 都实测正常。新建实例（`newinstance`）会一起带上。
- `sr mcai build` 会把 mod 装进所有实例。
- 实测过（2026-09-30）：两个实例同时启动、同时摆机位截图互不影响；同一实例同时发 4 个 `batch`（cam + shoot），四张图的机位都和各自的参数一致。

## 构建和安装

- `sr mcai build` = 用 JDK 17（`MCAI_JAVA_HOME`，sr 从配置 `SR_JAVA_HOME` 传；不给就用 PATH 上的 java，不到 17 就拒绝）跑 `./gradlew build`，再把 `build/libs/mcai-*.jar` 拷进所有实例和所有 `game/取材服务端*/` 的 `mods/`。
  `game/` 是各 worktree 共用的（符号链接），在哪个 worktree 跑 build，装的就是那里的代码：还没合并某个功能的 worktree 跑一次，就把它从游戏里换掉了
  （比如不含生成时修整的 jar 装进去，主世界服务端会读不进修整包，取材服务端.py 启动前会拦）。
- 编译要用到暮色森林的 jar（mixin 引用它的类），直接用 `game/取材服务端/mods/` 里那份，不另外下载。
  作者机器上 PATH 上和 `JAVA_HOME` 里的 JDK 是 8，编不了（所以 mcai 不读 `JAVA_HOME`，读 `MCAI_JAVA_HOME`）；手动跑 gradle 要先把 `JAVA_HOME` 指到 JDK 17、设好 `MCAI_GAME`。
- `game/` 在哪：mcai 只读环境变量 `MCAI_GAME`（sr 按配置 `SR_GAME` 传），各 worktree 共用同一个游戏环境。
- 第一次构建要下载 Gradle、Forge、反混淆 Minecraft，约 8 分钟（缓存在 `~/.gradle`）；之后十几秒。
- 改了 mod 代码要重启游戏才生效（`mcai game stop` 再 `start`）。
- 用的是官方 Mojmap；mixin 的 refmap 由 MixinGradle 生成。

### 实例要有的两处设置（`取材客户端` 已经设好，重建实例时照做）

| 文件 | 设置 | 原因 |
| --- | --- | --- |
| `game/实例/<实例>/instance.cfg` | `LowMemWarning=false`（要同时有 `OverrideMemory=true`） | 系统空闲内存低于分配值时 Prism 会弹确认框，没人点就永远卡在启动前，日志里只看到 `EnsureAvailableMemory` 开始、没有结束 |
| `.minecraft/config/fml.toml` | `earlyWindowControl = false` | 关掉 Forge 的早期加载窗口。开着的话它从进程启动就显示，mod 还没加载、藏不了；关掉后游戏窗口实测只闪现约 0.1 秒 |

## 不抢前台、输入锁定（默认行为）

- **窗口默认隐藏**：mod 在自己被构造的那一刻（mod 代码能在主线程上跑的最早时机）就 `glfwHideWindow`。
  截图是往离屏帧缓冲里画的，不需要窗口可见。实测窗口隐藏时：服务端 tick 照常（5 秒 102 tick）、区块照常加载、截图正常。
- **`mcai game start` 不抢前台**：启动前记下最前面的应用，启动期间每 0.3 秒检查一次，
  游戏或 Prism 抢到前台就用 `open <应用>` 还回去（不需要辅助功能权限）。
  实测两次启动：Prism 和 java 各抢到过 0.1～0.4 秒前台，随即被还回去；游戏窗口本身只以 0×0 的大小在屏幕上出现了 0.1～0.2 秒，等于没露面。
  管不到的一点：Prism 自己会在屏幕左上角显示一个约 480×180 的启动进度小窗 5～9 秒（不在前台）。
- **输入默认锁定**：鼠标移动/点击/滚轮、键盘在 mod 里直接丢掉，游戏也抓不到鼠标。
  即使窗口露出来被点到，机位不会动、不会触发交互、ESC 弹不出菜单。
- **`mcai input on`**：显示窗口并放开输入，给人自己进游戏操作；**`mcai input off`** 藏回去并重新锁定（同时把前台还给 `input on` 之前的应用）。
  `mcai state` 里的 `input`、`window.visible` 是当前状态。

## 空闲自动退出

- 游戏 **30 分钟**没收到 `mcai` 的请求（任何动作都算，包括 `state`、`ready`、`game status`），就自己走正常流程退出（会存档），Prism 也跟着退，不留进程。
- 起因（2026-10-03）：取材完没 `game stop`，游戏在后台空转了近 22 小时；合盖后 Mac 被 Wi‑Fi/蓝牙反复暗唤醒，醒着的时间里游戏照常跑，一夜把电池从 80% 耗到 22%。
- 不算空闲：有动作正在执行（跑很久的 `mesh`、`shoot`）；`input on` 期间（人在游戏里自己操作）。
- 计时用墙上时间，合盖睡眠的时间也算进去，醒来后半分钟内就退。
- 改时长：`mcai game start world=片场 idle=<分钟>`，`idle=0` 不自动退出。只管这一次启动（写进实例的 `config/mcai.idle`，不给 `idle` 时 `mcai` 会把它删掉）；游戏已经开着、`game start` 直接复用时不改。
- 自动退出后再发命令会提示连不上，`mcai game start world=片场` 重开（约 35 秒）。自动退出只是兜底，用完照样 `mcai game stop`。
- 实测（2026-10-03，`idle=1`）：40 秒时发一条 `state`，85 秒时游戏仍在；最后一次请求后约 75 秒游戏存档退出（时限 1 分钟 + 每 30 秒检查一次），Prism 同时退出，没有残留进程。

### 加新动作

在 `src/main/java/mcai/action/` 写一个实现 `Action` 的类（名称、说明、参数、跑在哪个线程、是否改世界），在 `Actions.java` 里 `register` 一行。
HTTP 接口（`POST /动作名`，请求体 `{"args": {...}, "cwd": "调用方目录"}`）和 `help` 都从注册表生成，不用另外登记。

## 坐标和朝向约定

- 坐标就是游戏坐标，写成 `x,y,z`。`cam` 的 `pos`、`state` 和截图元数据里的 `pos` 都是**镜头（眼睛）位置**，不是脚底。
- `yaw`：0 朝南（+Z），90 朝西（−X），180 朝北（−Z），−90 朝东（+X）。`pitch`：正值朝下，90 垂直俯视，−90 仰视。
  `look` 的朝向由 mod 计算，不用自己算角度。俯视时用 `yaw` 决定画面上方朝哪（`yaw=180` 上北）。
- `fov` 是**垂直**视角（度）。第一次 `cam` 起由 mod 接管，默认 70，之后沿用上次的值，`fov=0` 交还游戏。
  接管的原因：旁观模式在飞行，游戏会把设置里的 FOV 乘 1.1，不接管的话视角不固定（没调过 `cam` 时 `state` 里是 77）。
- `roll`：绕视线轴滚转（度），沿用上次的值，`roll=0` 复位。
- 截图元数据（`mcai meta 图.png`）：`pos`、`yaw`、`pitch`、`roll`、`fov`、`lens36`、`dim`、`dayTime`、`weather`、`frozen`、`world`、`size`。
  `lens36` 是按参考模型库机位格式换算好的 36mm 画幅焦距：`18 / (tan(fov/2) × 宽高比)`。
- 暮色森林维度 id 是 `twilightforest:twilight_forest`；这个种子的娜迦庭院中心在 `264, 488`，地面约 y=0。

## 各动作的行为细节

- **shoot**
  - 只调游戏的“画世界”那一步，HUD、准星、手、菜单都在它之外，天然拍不到；有界面开着也能拍（暂停菜单除外，见下）。
  - 拍之前要求连续 10 轮（每轮隔 30ms）都满足：镜头周围渲染距离内的区块到齐、网格编译队列为空、已加载区块总数不再变化。超时会说明卡在哪一条。
  - 输出尺寸任意（实测 1920×1080、1600×900、3840×2160），做法是临时把主帧缓冲改成输出尺寸再改回去。
  - 暂停菜单开着时（只有 `input on` 且按了 ESC 才会出现）集成服务端是停的，`shoot` 会直接报错让你先 `closescreen`。
- **freeze**：停的是服务端世界里的时间、天气、计划刻、随机刻、方块事件、方块实体、非玩家实体、自然刷怪和距离消失；
  玩家自己的 tick 和区块加载照常，所以冻结后仍可移动机位、加载新区块。客户端的时间推进也一并停掉。
  实测：冻结后 `time query gametime` 不变，半空召唤的盔甲架 2 秒后还在原位。
- **setblock / fill**：只通知客户端，不给邻居发方块更新（沙子不会马上掉、红石水流不触发）；邻居的形状更新照常（栅栏会连上、失去支撑的花会掉）。要完整原版行为用 `cmd setblock ...`。
- **undo**：动作执行期间，服务端每一次方块写入都先记下“改之前”的方块状态和方块实体数据，所以 `cmd` 里的 /fill、/clone、/place 也能撤销；
  期间新生成的实体（掉落物、召唤物）打上 `mcai` 标签，撤销时删掉。
- **cmd**：输出是命令反馈的文字；`success=false` 时 `mcai` 退出码为 1。集成服务端没有 `save-all`，存盘靠自动保存和退出。
- **天气**：`game start world=...` 进存档后会关掉天气循环并设成晴天（下雨挡画面，也拖慢渲染）。剧情要雨就 `mcai cmd execute in minecraft:overworld run weather rain`（天气存在主世界里，在暮色森林里直接 `weather ...` 不生效），设了不会自己变；重启游戏回到晴天。
- **game start**：带模组维度的世界第一次在客户端打开会弹“实验性设置”确认，`mcai` 会自动点“继续”（每个存档只问一次）。

## 导出场景网格（mesh）

```sh
sr mcai cam pos=8,120,232 pitch=90 yaw=180 dim=twilightforest:twilight_forest    # 先把镜头挪到区域附近，区块要在渲染距离内
sr mcai mesh from=-40,0,195 to=56,95,270 out=../参考模型库/src/模型/场景/巫妖怪塔.网格 mark=twilightforest:lich_boss_spawner
```

- 做法：不自己解析方块模型，让游戏的渲染器把区域里的东西画一遍，把它吐出来的面接住。所以拿到的就是游戏实际画的面：
  被不透明方块挡住的面本来就不出（地下实心部分一个面都没有）；楼梯、栅栏、玻璃、模组异形方块、群系染色、环境光遮蔽都是渲染器算好的。
- 实体也导：画、物品展示框、盔甲架这类不会动的实体，以及箱子、告示牌、刷怪笼这类方块实体，调它们各自的渲染器。
  生物、掉落物默认不导（`entities=all` 才导，按当前姿势定格），`entities=0` 只要方块。结果里 `entities` 是导了的，`entitiesSkipped` 是跳过的。
- 输出 `out.json`（范围、原点、各层面数、标记点）、`out.bin`（顶点，gzip 压缩）、`out.png`（只含用到的贴图的小图集）。
  `out.json` 的 `sprites` 列出小图集里每张贴图的名字和位置，要按方块贴图取图集坐标就按名字查它，不要手写坐标、不要逐像素反推；
  `取材` 记着实例、存档、维度、mesh 参数、模组版本和资源包。同一区域、同一世界状态重导，图集排布和面的顺序不变。较早导出的网格没有这两项。
  贴图本来就只存一份（每种贴图在小图集里一格，几十到一百多 KB）；文件大的是顶点，每个面 4 个顶点各带位置、贴图坐标、颜色。gzip 后约为原来的 1/6（终焉高原城堡 123MB → 22MB）。
  参考模型库里用 `src/lib/方块网格.tsx` 的 `BlockMesh` 渲染，写法照 `src/模型/场景/巫妖怪塔.tsx`；导出后在 `地标预览` 这个 Composition 里加一项核对。
- **自动分块**：范围超出镜头的渲染距离时，mod 自己把镜头挪到每一块（128×128 格）正上方、等区块到齐再导，面攒在同一份输出里，导完镜头还回原处。
  实测终焉高原城堡 1026×316 格分 27 块，40 秒左右。
- **优化**（都在导出时做，参考模型库不用管）：
  - 被挡住的面渲染器本来就不出；被树叶六面包住的树叶不导（最外一层照常六面都出）。
  - 同一平面上挨着的、贴图和颜色都一样的整格面拼成大面（`merge=0` 关掉），贴图在大面上平铺；带环境光遮蔽渐变的面不合并。
    为了让同一群系里的草和树叶颜色完全一致，导出时不做群系之间的颜色过渡。
  - 结果里的 `quadsByBlockBeforeMerging` 列出最占面数的方块，面数太多时据此用 `skip` 去掉不需要的（比如城堡周围森林的树）。
- 没有碰撞体积的方块（花草、蘑菇、火把、藤蔓）单独一层 `plants`，参考模型库里可以按矩形把角色跑位上的草清掉（`clearPlants`）。
- 个别模组方块画不出来时跳过这一块，记在 `entitiesSkipped` 里（`（方块渲染出错）`），不让整个导出失败。
- `outside=1`：只要从外面看得到的（从区域顶上往里灌，灌不到的封闭洞穴不导）。大范围地形用；要拍室内的建筑不要开，封死的房间会被去掉。
- `origin=x,y,z` 导出坐标的原点，默认区域底面中心；`skip=firefly,*vine*` 不导的方块；`mark=方块id` 把这些方块的位置记进 json。
- 用图集的贴图（方块、箱子、告示牌、画、展示框里的物品）按小贴图放进导出的图集；不在图集里的实体贴图只抠用到的那一块。
- 实测（2026-09-30）：巫妖怪塔 112×96×79 格，8.8 万个有面的方块、15.2 万个面、99 幅画、11 个箱子，导出约 1 秒，bin 15MB。
  终焉高原城堡整个范围（分 27 块、`outside=1`）：不去东西 795 万个面、763MB，其中荆棘 440 万；去掉荆棘和周围森林的树、草后 115 万个面、130MB。
  娜迦庭院 191×70×191：39 万个面、44MB（大头是树叶，树叶带环境光遮蔽，合并不了多少）。
- 限制：
  朝向明暗没有烘进去（交给参考模型库的灯光）；贴图动画只取当前一帧；模型在渲染时才定贴图的少数模组方块，对不上贴图的面会丢掉并在结果里报 `quadsWithoutTexture`。

## 暮色森林放大 4 倍（数据包 + 地标网格）

用户 2026-10-04 定：不再自己写 16 倍地形，「全面改成原版的巨型生物群系（4x）吧，在游戏里面生成真实的地貌，然后导入」，暮色森林也放大 4 倍。
原版的巨型生物群系管不到暮色，所以分两半做，**两半缺一不可**：

- **数据包** `sourcing/datapacks/暮色放大4倍/`：覆盖暮色的群系层栈 `random_forest_biomes`，在原层栈外面再包两层 zoom（盐 2000、2001，不模糊），群系边长放大 4 倍。
  溪流层（`biomes_along_streams`）引用的就是它，所以溪流跟着新的群系边界走，宽度不变（用户 10-04 定：溪流先不加宽）。
- **mod 里的 mixin**（`TwilightGrid`、`mixin/LegacyLandmarkPlacementsMixin`、`mixin/ChunkGeneratorTwilightMixin`，终焉城堡另有两个，见下面「mixin 改了哪些地方」）：暮色的地标（首领建筑、小丘、树篱迷宫）摆在写死的 16 区块网格上，数据包改不了。
  只放大群系的话，一个关键群系里会落进十几个网格点，同一种首领建筑重复十几座。mixin 把网格放大到 64 区块（1024 格），中心的抖动也乘 4，得到原版布局整体放大 4 倍；建筑本身大小不变。
  mod 只认数据包里的标记文件 `data/mcai/twilight_x4.json`：服务端启动时（早于任何区块生成）有这个文件就放大，日志里打一行「暮色地标网格：64 区块」，没有就照原版 16 区块。
  所以旧的片场存档不受影响，客户端实例的集成服务端补生成区块时也和已有区块对得上。

只有数据包没有 mod：首领建筑重复十几座；只有 mod 没有数据包：什么都不放大。

### 新建放大 4 倍的世界

用户 2026-10-04 定种子 1752，世界名 `暮色放大-1752`。候选和俯视图在 `参考模型库/预览/暮色放大/`（`参考模型库/工具/游戏取材/暮色选种/选种.py` 离线扫出来、画出来的），
1752 的 7 座首领地标（游戏 x, z）：娜迦庭院 (-11191, -887)、巫妖塔 (-9015, 1032)、九头蛇巢 (-6327, 2184)、黑暗塔 (-7159, 5064)、
雪怪洞 (-3959, 5192)、极光宫殿 (-2935, 5128)、终焉城堡 (-3127, 2120)。下面的命令都在项目根下执行。

1. 服务端和所有客户端实例都装同一版 mod（`sr mcai build` 一次装齐）。
2. 建世界，当场在暮色里查 7 座地标（不带预生成模组）：
   ```sh
   python3 参考模型库/工具/游戏取材/取材服务端.py --world 暮色放大-1752 --new --seed 1752 --twilight-x4 \
     'execute in twilightforest:twilight_forest positioned -11191 64 -887 run locate structure twilightforest:naga_courtyard' \
     'execute in twilightforest:twilight_forest positioned -9015 64 1032 run locate structure twilightforest:lich_tower' \
     'execute in twilightforest:twilight_forest positioned -6327 64 2184 run locate structure twilightforest:hydra_lair' \
     'execute in twilightforest:twilight_forest positioned -7159 64 5064 run locate structure twilightforest:dark_tower' \
     'execute in twilightforest:twilight_forest positioned -3959 64 5192 run locate structure twilightforest:yeti_cave' \
     'execute in twilightforest:twilight_forest positioned -2935 64 5128 run locate structure twilightforest:aurora_palace' \
     'execute in twilightforest:twilight_forest positioned -3127 64 2120 run locate structure twilightforest:final_castle'
   ```
   `--twilight-x4` 在第一次启动之前把 `sourcing/datapacks/暮色放大4倍` 放进新世界的 `datapacks/`（连同 `sourcing/datapacks/通用/` 下的），服务端 `mods/` 里没有 mcai 的 jar 会拒绝。
   世界目录 `datapacks/` 里的数据包会自动启用，排在暮色自己的数据之上，同名文件以它为准。已经生成过的暮色区块不会跟着变，放晚了只能删掉新世界重来。旧的 `world/` 不动。
3. 核对：
   - 服务端的 `logs/latest.log`（脚本不打印启动日志）：有 `Found new data pack file/暮色放大4倍, loading it automatically`（只在第一次）和「暮色地标网格：64 区块」，
     没有 mixin 报错（mixin 配置要求每个注入点都找到，找不到会直接崩）：`grep -E 'Found new data pack|暮色地标网格|[Mm]ixin.*(rror|xception)' game/取材服务端/logs/latest.log`。
   - 从预测的地标中心查，7 条 `locate` 报的距离都应在一个区块以内；报出几百上千格，说明那个网格点上不是这座建筑，和选种时预测的对不上，先别预生成。
     终焉城堡的主楼就在它的地标中心上。也可以把 `locate structure ...` 换成 `tf center`，它报最近的地标中心和那里是哪种地标。
4. 预生成：7 座地标的外包框是 x -11191～-2935、z -887～5192（8.3 × 6.1 km），四边各外扩 2 km，用 Chunky 生成完整区块：
   ```sh
   python3 参考模型库/工具/游戏取材/取材服务端.py --world 暮色放大-1752 --pregen chunky \
     'chunky world twilightforest:twilight_forest' 'chunky corners -13191 -2887 -935 7192' 'chunky start' \
     'wait:Task finished for twilightforest:twilight_forest'
   ```
   `chunky corners` 把中心设成两角的中点、形状设成长方形。范围 12.3 × 10.1 km，767 × 631 = 48.4 万个区块、124 km²。
   2026-10-04 实测：Chunky 累计 1 小时 55 分（平均 70 区块/秒，每秒的速率 17～142、中位 80，终焉高原、荆棘之地一带最慢），
   暮色维度 region 3.5 GB（约 29 MB/km²），整个世界目录 3.6 GB。中间出过两件事，照下面的办法接着跑：
   - 一次开服跑了约 27 万区块后堆满（6 G 堆，老年代 99.9%，每秒一次 Full GC，速度掉到 36 区块/秒），内存里压着约 11 万个没卸的区块
     和 2900 万个计划刻。计划刻约 99% 是树叶（林冠树叶、暮色橡树叶、云杉叶）在生成树时排下的，没有玩家的服务端区块不 tick，
     它们一直留着、随区块存进存档（每区块平均三百多个）；区块为什么没卸没查清。所以一次开服别跑太多：停服（脚本的正常停服）后
     `'chunky continue'` 接着跑，Chunky 的进度存在 `config/chunky/tasks/` 里。
   - 读方块碰上调色板扩容的原版数据竞争（arm64 上容易碰）会让光照线程停掉、预生成卡死（见 `mixin/LevelChunkSectionMixin`，已修）。
   跑完以后同一个矩形再 `'chunky start'` 一遍：生成完的区块几秒就扫过去，只补中途卡住、强杀留下的空洞（这次补了 2 个停在
   initialize_light 的区块）。生成完的区块数可以拿 `Status` 是 `minecraft:full` 的数核对。
5. 片场存档照常 `sr mcai game copyworld name=<存档名> from=暮色放大-1752`，数据包跟着世界目录一起复制。

### mixin 改了哪些地方

暮色 4.3.2508 里所有按网格找地标的代码都走 `LegacyLandmarkPlacements` 的五个方法（字节码里逐条查过）：
`getNearestCenterXZ`（网格中心）、`pickLandmarkForChunk` 和 `getFeatureForRegion`（地形改造取群系的点）、`pickVarietyLandmark`（普通森林里的地标、每 8×8 格强制一组娜迦庭院和巫妖塔）、`landmarkCenterScanner`（`/locate`）。
用到它们的有：结构起点、地标附近起丘和压平、暗林树冠给黑暗塔让位、`/tf center`、装饰避让、魔法地图、进度限制、传送门落点、树篱迷宫刷怪。
别处另写死了网格的有两样，也一并改了：

- 云中小屋云层的形状（`ChunkGeneratorTwilight.deformTerrainForTrollCloud2`）另算了一遍网格编号，换成 64 区块的（`ChunkGeneratorTwilightMixin`）。
- 终焉城堡按 256 格（16 区块）的网格摆：主楼吸到 256 格网格点上（`FinalCastleMainComponent` 构造函数里 `x + 127 >> 8 << 8`），
  迷宫塔限定在「主楼旁边的 256 格网格点」128 格以内（`FinalCastleMazeTower13Component.buildContinueTowerTowards`）。
  原版起点区块离网格点不超过 3 个区块，吸过去正好是网格点；64 区块网格下主楼会相对起点区块偏 -71、-7、+57、+121 格之一，
  偏 +121 时主楼超出原版 8 区块的结构引用半径，城堡被切掉一截（离线测试里 44% 的城堡会这样），位置也和 `/tf center`、选种图差约 120 格。
  改成：主楼放在 64 区块网格的地标中心（`FinalCastleStructureMixin`，主楼刚造好时整体平移），迷宫的城堡中心取主楼中心
  （`FinalCastleMazeTower13ComponentMixin`，原版主楼就在网格点上，所以和原版是一回事）。这样主楼和迷宫塔都在起点区块 ±8 个区块里，
  城堡坐标就是选种图上标的地标中心。不是地标中心区块的城堡（别的维度里 `/place` 的）不动。
- 终焉城堡外围的残塔、废塔（迷宫塔随机往外接，`buildDamagedTower`）原版不限远近，会伸出起点区块 ±8 个区块的引用半径，伸出去的部分不生成。
  2026-10-04 种子 1752 第一次建的世界里，主楼周围 188 件结构件有 14 件超出：两座废塔整座没有，两座残塔外墙切掉 1、3 排，荆棘和桥切断。
  改成：伸出引用半径的残塔、废塔当作撞上了别的结构件，暮色换个方向或不接（`FinalCastleMazeTower13ComponentMixin` 的 `mcai$collideOrOutOfReach`，
  判断在 `TwilightGrid.castleTowerFits`）；迷宫塔连屋顶也这样查（离中心正好 127 格的屋顶会伸出 1 格）。重建后的城堡 182 件全在引用半径里，
  入口塔、钟楼都在。原版 16 区块网格的城堡同样会切（主楼离起点区块还更远），旧片场存档（开关关着）不动。
  另外暮色原版有个笔误：地牢出口往下一层的台阶 `x` 取了 `z`（`FinalCastleDungeonExitComponent` 里两处都是 `minZ + 15`），
  第二层以下的地牢落到 x = z 那条对角线上（种子 1752 这座在 5 千多格外），离起点区块太远，从来不生成，不影响地面上的城堡，没改。

查法：暮色 jar 的 1570 个类全部反编译，再扫字节码里的 `>> 8`、`<< 8`、`>> 9`、`>> 10`、256、255、-256、512、1024 等常量，逐处看和网格有没有关系。
其余写死尺寸的都没改，和地标网格无关或不影响取材：

- `TFTerrainWarp`（群系交界的地形平滑，±2 个 4 格）：和网格无关，所以 4 倍大的高地边缘比原版陡。
- 魔法森林的草和树叶颜色（`BiomeGrassColors.getEnchantedColor`）：彩虹圈以 256 格网格点为圆心。放大后一片魔法森林里有十几个圈心，和任务林地也对不上；只是颜色。
- 魔法地图的中心（`MagicMapItem.getMagicMapCenter`，2048 格一格）和找不到安全落点时传送门往「关键群系之间的中心」挪
  （`TFTeleporter.moveTowardsCenter` 用同一个函数）：对齐的是关键群系的 2048 格大格，数据包放大后大格是 8192 格，没跟着放大；取材不用魔法地图和传送门。
- `LandmarkBiomeSource`（1024 格）：另一种群系源，暮色森林维度不用它。

  1. 编解码（`JigsawStructure.CODEC`）：size 只收 0～7、半径只收 1～128，半径加地形适配 12 格 ≤ 128。→ 放宽到 size 0～64、半径加适配 ≤ 1024，读法和原版一样。

  3. 取起点（`StructureManager.fillStartsForStructure`）：起点区块在 8 个区块外时超出这一步的 `WorldGenRegion`，原版直接崩。→ 拿不到就用算出来的那份。
  4. 读存档（`ChunkSerializer.unpackStructureReferences`）：读区块时丢掉 8 个区块外的引用（打 WARN「invalid structure reference」）。→ 引用半径以内的留着。
  地形给结构让位（Beardifier）和 `/locate` 都按引用找结构，跟着 2～4 就对了。
  引用半径按这个世界里最大的拼图结构算，服务端启动时打一行「大拼图结构：minecraft:ancient_city size 40、半径 440 格，引用半径 34 区块」。
  没有超出原版范围的结构（老片场、暮色世界）就是 8，和原版一模一样，所以别的世界不受影响。

只有数据包没有 mod：服务端读不进数据包（size 超范围），起不来；只有 mod 没有数据包：什么都不变。

用户 2026-10-04 定「不找天然的，直接修整」，以后还会要山、平地、峡湾、湖，所以做成通用的、加区域和操作就行的机制；

做法：mod 注册两种密度函数（`src/main/java/mcai/terrain/`），数据包 `sourcing/datapacks/主世界修整/` 覆盖史诗地形的某个密度函数文件，把原内容原样包进 `mcai:edit`，
在区域里改这个量。海底、海岸、群系、地表方块、树都由游戏照常生成，游戏截图、`mcai mesh` 导出、DH 远景是同一片地。
区域外权重正好是 0，原值原样返回，一格都不变。

### 数据包怎么配

- `sourcing/datapacks/主世界修整/`：`pack.mcmeta`；`data/etn/worldgen/density_function/overworld/continents.json` 是覆盖文件；
  `data/mcai/worldgen/density_function/region/*.json` 是区域（单独成文件，几个覆盖文件可以共用一个区域）；`data/mcai/worldgen/noise/*.json` 是边界噪声。
  区域和修整的具体数值看文件本身（由岛与扇面的设计定）。
- **区域** `mcai:region`，值是 0～1 的权重：形状里面离边界 `falloff` 格以上是 1，边界上和外面是 0，中间 smoothstep 过渡。
  ```json
  { "type": "mcai:region", "shape": <形状>, "falloff": 3000, "edge": <密度函数，可省，默认 0> }
  ```
  形状的坐标是游戏坐标 `[x, z]`（x 朝东、z 朝南），朝向按罗盘（0 = 北、90 = 东），长度单位是格：
  - `{"type": "circle", "center": [x, z], "radius": r}`
  - `{"type": "sector", "center": [x, z], "facing": 度, "half_angle": 度, "radius": r}`：半角 ≥ 180 就是整圆
  - `{"type": "polygon", "points": [[x, z], ...]}`：至少 3 个点，可以凹
  - `{"type": "path", "points": [[x, z], ...], "width": w}`：折线两边各 w/2 的带子（峡湾、河道），至少 2 个点

  `edge` 加在「到边界的有向距离」上（格，正 = 边界往里缩），填一个噪声边界就不是几何直线、圆弧。clamp 到 ≥ 0 时形状本身就是外边界，形状外一格都不变；
  有负值时边界最多往外推 `-edge` 的下界那么多格。edge 只用随 x、z 变的（噪声的 `y_scale` 写 0）：区域通常包在 `cache_2d` 里，一列只算一次。
  形状的边是直线、圆弧，从基地看不出，从别处航拍看得出（2026-10-05 复核：扇面两条边各留下十几公里的直海岸）：加大 edge 的幅度和波长，或者用多边形沿天然海峡走。
- **修整** `mcai:edit`：把 `input` 按顺序套上几条修整，每条是「区域 + 操作 + 目标值」。
  ```json
  { "type": "mcai:edit", "input": <原内容>, "edits": [ { "region": "mcai:region/xxx", "op": "toward", "value": -0.8 }, ... ] }
  ```
  `op`：`toward` 往目标值拉（权重 1 时等于目标值）、`add` 加上 权重×value、`min` 只往下压到目标值、`max` 只往上抬到目标值。
  `value` 可以是数，也可以是密度函数（带噪声的目标）；`region` 可以是任何密度函数（比如区域乘一个数），值大于 1 按 1 算、不大于 0 这条跳过。
- **覆盖哪个密度函数**：要改哪个量就覆盖哪个文件，原内容原样放进 `input`，外层的 `cache_2d`、`flat_cache` 留在外面。
  - 现在覆盖的是大陆度 `etn:overworld/continents`：它经 `minecraft:overworld/continents` 流到地形（offset、factor、jaggedness）和噪声路由的 continents（群系），
    海陆和海洋群系一起变。目标值不能低于 -1：史诗地形的 offset 样条在大陆度 ≤ -1.05 时走山那一支。
  - 温度（只影响群系挑哪个，比如不让修出来的海是冻洋）：`etn:overworld/temperature`（`flat_cache` 包着 `shifted_noise`，修整放进 flat_cache 里面）。
    山的强度、侵蚀这些在史诗地形的 `data/etn/worldgen/density_function/overworld/` 下找对应文件（解开的在 `game/缓存/选种/史诗地形/`）。
  - 覆盖文件去掉 `mcai:edit`（换回它的 input）要和史诗地形的原文件一字不差：离线工具读包时核对（`地形.mjs` 的 `核对覆盖`），史诗地形更新、原文件变了就报错。
  - 世界 `datapacks/` 里的包按 id 排序加载，后面的盖前面的：`file/主世界修整` 排在 `file/epicterrain_compatible1.20.zip` 之上（2026-10-05 临时世界实测）。改名字前想想排序，取材服务端.py 开服后会查。
- **读包是严格的**：字段写错、类型名拼错、数超范围，游戏读不进来（专用服务端起不来，客户端停在数据包错误界面），离线版也报同样的错。
  1.20.1 的 DFU 遇到「可省字段」写错会悄悄当成没写，`edge` 另写了严格的读法；deepslate 遇到写错的类型名会悄悄当成 0，`生成修整.mjs` 也拦了。
- **许可**：覆盖文件里抄了史诗地形 compatible 1.0.3 的大陆度样条点，这个版本在 Modrinth 上标的是保留所有权利（All Rights Reserved）。

### 加一种形状、一种操作

- 形状：`Shape.java` 加一个 record（`distance` 给有向距离、`box` 给包围盒、`type`），`permits` 和 `codecOf` 各加一处；`生成修整.mjs` 的 `parseShape()` 加同样一支
  （三角函数只在解析时算一次，逐列只用加减乘除和 sqrt，两边才逐位一致）；`test/terrain-edit-cases/` 加一个用它的区域、`points.json` 加它的框、`bad-cases.json` 加它的错误写法。
- 操作：`TerrainEdit.Op` 加一个值、`compute` 的 switch 加一支、`minValue`/`maxValue` 按最宽的算；`生成修整.mjs` 的 `editOps` 列表、`Edit.compute` 和取值范围同样加；用例加一个用它的修整。
- 新写的密度函数类：`mapAll` 先把 visitor 传给每个子密度函数、再 `visitor.apply(新对象)`（噪声才接得上）；`minValue`/`maxValue` 要是真的上下界，宁宽勿窄
  （原版拿它做 min/max 的短路和样条的取值范围，窄了会出怪地形）；`equals`/`hashCode` 按内容比；类型名登记在 `TerrainTypes.CODECS`。

  量修整出来的岛，出对比图（用法见它的文件头）。2026-10-05 定稿包的结果见 `sourcing/datapacks/主世界修整/说明.md`「游戏核对」。
- 专用服务端：jar 不含修整时读数据包失败，日志 `Registry loading errors` … `Unknown registry key in … density_function_type]: mcai:edit`，
  接着 `Failed to load datapacks, can't proceed with server load` 退出；不带 `--safeMode` 不会退回原版数据（2026-10-05 用一个类型名拼错的包实测）。
  取材服务端.py 启动前就查 jar，开服后查 `/datapack list`，日志出现这些行就停服报错。
- 客户端：
  - 「实验性设置」提示（Worlds using Experimental Settings are not supported）：每个存档第一次在客户端打开时弹一次，和修整包无关：
    世界数据包读进来的世界生成设置都算实验性，只开原版是 Stable，加上史诗地形就是 Experimental，再加修整包还是 Experimental（离线用游戏的读包代码算的，没在客户端实测）；
    暮色维度也会触发。`mcai game start` 自动点继续。
  - 安全模式提示（Errors in currently selected data packs prevented the world from loading，按钮 Safe Mode）：只在实例的 mcai 不含修整、或修整包写坏了时出现。
    **千万别点**：安全模式只用原版数据，史诗地形和修整都被丢掉，之后补生成的区块是原版地形，存档也记成只开原版数据包。`mcai game start` 碰到这个界面直接报错退出，不替你点。

### 性能

2026-10-05 离线实测（`--性能`，用游戏的 `NoiseBasedChunkGenerator`，单线程；游戏里区块分在几个线程上生成，每块的相对开销应当一样，未进游戏核实）。
修整包是最终那一版（sourcing/datapacks/主世界修整，30°～240°，base_sea 是 209 个点的多边形）：
- 区域每次求值（点在形状的包围盒内外都有）：不带边界噪声的 7～13 ns，带边界噪声的 35～166 ns（边界噪声只在过渡带附近算，形状外和深处跳过）；多边形 4、64、256、1024 个点分别约 18、155、415、1421 ns，点数别上千。
- 噪声路由的大陆度（不经区块缓存）每次 3232 ns → 加修整 4809 ns（+49%）。
- 整块区块生成（群系 + 噪声两步，4×4 区块一组，加修整前后交替量）：
  - 区块 (2010, -230) 起（岛西 7.9 km，`base_sea_ramp` 的过渡带，在 `base_sea` 的包围盒里、多边形外）：群系 10.76 → 15.13 ms/块（+40.7%），噪声 21.74 → 21.60（−0.6%）。
  - 区域外（区块 (0, 0)，所有区域的包围盒外）：群系 9.05 → 10.89 ms/块（+20.3%），噪声 21.28 → 20.70（−2.7%）。
  - 两步合计：前一处 +13%，区域外 +4%。噪声这一步的差在量测抖动以内。
  - 核查（同一天，同一版区域、142 点多边形）量的是群系在修整区和过渡带 +35%～42%、区域外 +14%～16%，大陆度单次 +23%～39%。
  - 更早写在这里的 群系 +3.6%～10.4%，是改区域（换成沿海峡的多边形、加温度等气候量的修整）以前那版包量的，已过时。
- 群系这一步慢，是因为 9 个覆盖里有 5 个是气候量（温度、湿度、侵蚀、怪异度、大陆度），群系取样时 `cache_2d` 几乎不命中；
  温度那条修整没有缓存，每次都要算一遍多边形的距离。区域外（包围盒外区域直接返回 0）也慢 20%，没再细分是哪一层。噪声这一步不受影响。
- 最初的实现 equals 按对象比，游戏接噪声（`RandomState`）和建区块缓存（`NoiseChunk`）时按 equals 合并重复引用，大陆度被引用的几处并不成一个，
  各算一遍史诗地形的大陆度样条：同样量，群系一步慢 44%～61%、噪声一步慢 28%～36%（连区域外都慢）。所以新写的类一定按内容比，测试第 7 项会拦。

## 已知限制

- **锁屏时能否截图：没有实测。** 做验收时用户正在用这台电脑，没有去锁他的屏。
  已实测的是：窗口隐藏、窗口在后台（VS Code 在前台、游戏窗口无焦点）、窗口在前台三种情况截图都正常。
  原理上截图不经过屏幕（离屏帧缓冲），但锁屏后 macOS 是否会给进程降速没验证过；要验证就先 `sleep 20; sr mcai shoot out=x.png`，再按 Ctrl+Cmd+Q 锁屏。
- 冻结只停服务端。客户端自己的动画照常：粒子、萤火虫、水面贴图、生物的待机摆动。所以同一机位连拍两张，这些地方会有像素差异。
- undo 的边界：
  - 只改方块实体数据而不换方块的操作（`/data merge block`、往箱子里放东西）不记录；
  - 动作返回之后才发生的连锁变化（沙子下落、水流）不算在内——要撤得干净，先 `freeze` 再改；
  - 被命令删掉的实体不会复活；撤销记录不跨游戏重启。
- `batch` 不是“同一个 tick 内执行”（`shoot` 要跨很多帧），只是按顺序；需要画面静止就先 `freeze`。
- `batch` 的每一步会按 shell 规则再拆一次词，步骤里的双引号（NBT 字符串）要写成 `\"`；不想转义就别放进 batch，单独调用。
- zsh 里带方括号的选择器要加引号：`sr mcai cmd 'kill @e[type=item]'`。
- 发光描边（发光效果的实体轮廓）不会出现在截图里。
- 游戏在跑但窗口隐藏时，它照样按正常帧率渲染，一个实例常驻占 2 个核左右和 GPU；不用时 `mcai game stop`（忘了的话空闲 30 分钟后自己退，见「空闲自动退出」）。
- 进别的服务器（`server=`）时只能看和拍，摆机位要靠那边的权限自己发命令；没有实测过。
- 玩家死亡时的死亡界面 `closescreen` 关不掉（实测：游戏立刻重新打开它）。要用 `mcai click text=重生`，但按钮在界面出现后约 1 秒内是灰的，得等一下再点（等够时间后点击能否重生没有实测）。当摄像机用的旁观模式玩家不会死，正常取材碰不到。
